# 卡住任务恢复与候选扫描超时设计

## 背景

实机上存在三类容易被误认为“正在执行”的状态：等待源目录完整、等待 CloudDrive2 上传，以及远程候选目录扫描。当前实现会把所有非终态都计入“当前执行”；上传队列缺失或进度不再变化时会永久保持 `waiting_cd2_upload`；远程候选扫描则在 Web 请求中同步调用 CD2 流式接口，没有截止时间，页面可能一直显示“读取中”。

已有实例中，`Grace 2025` 和 `Mona Lisa 1986` 的 ISO 已写入 CD2 挂载目录，但没有可靠的上传完成证据，任务持续等待超过一天。`Slither 2006` 缺少 `BDMV/STREAM`，属于正常的源目录等待，不应被当成正在封装或允许绕过完整性检查。

## 目标

1. CD2 上传连续 30 分钟没有字节进展时结束无限等待，转为可见、可操作的异常。
2. 已连接且状态新鲜的 CD2 队列连续 30 分钟找不到对应任务时，同样转为可操作异常。
3. 等待和上传异常任务提供上下文操作，用户不再只能看状态。
4. 远程候选目录扫描必须有截止时间和单任务保护，页面不能无限“读取中”，也不能因反复点击累积阻塞线程。
5. “当前执行”只统计真正占用本机 worker 的任务；等待任务继续可见，但单独计数。

## 非目标

- 不自动把停滞或队列缺失的上传判定为已交付。
- 不删除、覆盖或重命名 CD2 挂载目录中的 ISO。
- 不允许绕过 BDMV / VIDEO_TS 结构完整性检查。
- 不提供强制终止正在写 ISO 或正在复制大文件的进程；这类中断可能留下大体积残留文件。
- 不重构 CD2 客户端或整个扫描器架构。

## 上传等待看门狗

`waiting_cd2_upload` 条目记录最近一次有效观测：当前字节数、总字节数、百分比、最近进展时间和最近轮询时间。

- 首次看到匹配上传任务时初始化进展基线。
- 当前字节数或百分比增加时，刷新最近进展时间。
- 上传完成时沿用现有逻辑，转为 `transfer_done`。
- CD2 未连接、返回状态不新鲜，或距上一次有效观测超过 `max(60 秒, 3 × cd2_queue_poll_seconds)` 时暂停计时；恢复连接后的第一次有效观测只重建基线，不参与停滞判定，避免把 API 故障误判为上传停滞。
- 在持续获得有效状态的前提下，匹配任务连续 30 分钟无进展时转为 `transfer_failed`，失败码为 `cd2_upload_stalled`。
- 从未看到匹配任务，且持续 30 分钟获得“队列中不存在”结果时转为 `transfer_failed`，失败码为 `cd2_upload_missing`。

异常只改变任务状态并保留目标路径、上传快照和文件；不会删除文件，也不会自动重新上传。

## 人工处置

封装中心的任务列表展示所有非终态任务，而不只展示带输出路径的任务。按钮按状态出现：

- 源目录等待（`receiving`、`waiting_partial`、`waiting_stable`、`waiting_cd2_pull`、`waiting_cd2_confirm`）：显示“重新检测”。它复用现有安全检查；结构仍不完整时只返回原因，完整后才进入现有封装流程。
- CD2 上传等待，以及 `cd2_upload_stalled` / `cd2_upload_missing` 异常：显示“重新检测”和“确认已上传”。
- “重新检测”清除本次上传监控异常、重置观察窗口，并在后台立即轮询一次 CD2 状态。它不修改文件。
- “确认已上传”是显式人工确认。后端必须确认任务目标仍位于允许的 CD2 成品目录、文件存在且大于 0 字节、ISO 结构校验通过；如果状态中已有可靠的目标字节数，还必须与实际文件大小一致。全部通过后才标记 `transfer_done`，并记录确认时间和人工确认标记。它不删除源文件或目标文件。

现有“清理残留并重试”只继续用于可重新封装且源目录仍存在的失败项；上传监控异常不再错误地引导用户重新封装已删除源目录的任务。

## 远程候选扫描

远程候选扫描增加一个进程内单任务控制器：

1. 同一时刻只允许一个候选扫描运行。
2. 扫描在后台线程中使用独立的 CD2 客户端，避免卡住共享的上传状态轮询客户端。
3. 控制器最多等待 15 秒；超时后关闭该独立客户端以取消 gRPC 流，并返回明确的“扫描超时”状态。
4. 如果底层调用仍未退出，后续请求直接返回同一超时状态，不再创建更多扫描线程；原线程退出并释放控制器后才允许下一次扫描。
5. 保留最后一次成功结果；超时时可返回旧结果并标注 `stale`，没有缓存时返回空列表和可见错误。
6. 前端请求再设置 20 秒超时作为最后保护；无论成功或失败，刷新按钮都会恢复可点击。

自动拉取复用同一个受控扫描入口。扫描失败或超时时本轮不创建拉取任务，下一轮继续尝试，不影响本机封装和上传状态轮询。

## 统计语义

`stats.active` 仅统计 `running`、`transferring`、`refreshing_cd2_dir` 等真正占用本机 worker 的状态，再加正在执行的文件操作。其他非终态计入新增的 `stats.waiting`。首页仍显示最需要关注的等待任务摘要，但“当前执行”不再把下载等待和上传等待伪装成运行中的 worker 数量。

## 接口与错误处理

- 新增任务动作接口，仅接受已登录请求、受支持的动作和状态中的精确源路径。
- 所有路径重新解析后必须落在配置的监控目录或 CD2 成品目录边界内，不能信任前端传入的目标路径。
- 并发动作通过现有状态锁串行校验；终态任务重复确认按幂等成功处理。
- 重新检测在后台执行，接口快速返回，页面依靠现有状态轮询刷新。
- 手工确认、自动超时和恢复检测均写入状态事件及日志中心。

## 测试策略

新增标准库单元测试并继续运行现有 smoke：

- 上传字节增加会重置 30 分钟计时。
- 连续无进展达到阈值后转为 `cd2_upload_stalled`，文件和目标路径保持不变。
- 队列持续缺失达到阈值后转为 `cd2_upload_missing`。
- CD2 断线或轮询断档不会直接触发停滞异常。
- “重新检测”恢复等待并重置监控字段；“确认已上传”只接受允许目录内且校验通过的 ISO。
- 下载未完成任务的重新检测仍被完整性门禁阻止。
- 候选扫描在截止时间内返回正常结果；超时恢复页面按钮，且重复请求不创建额外扫描线程。
- 首页活动统计排除等待状态并单独返回等待数量。
- 前端契约测试确认对应按钮、动作请求和候选请求超时存在。

## 影响范围

- 后端：上传等待状态机、任务人工动作、候选扫描控制器、统计口径。
- 前端：封装中心任务行操作和候选请求超时反馈。
- 文档：README 的上传等待、人工处置和候选扫描语义。
- 测试：`test_app.py` 与现有 smoke 契约。
