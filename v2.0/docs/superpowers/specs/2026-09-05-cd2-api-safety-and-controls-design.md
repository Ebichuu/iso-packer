# CD2 API 安全链路与任务控制设计

## 背景

ISO Packer 已经通过 CloudDrive2 gRPC API 读取上传、下载和复制任务，并使用挂载目录完成 ISO 上传。官方 API 还提供了明确的上传状态枚举、复制冲突策略、复制任务控制、目录缓存失效、实时推送和运行时诊断能力。

当前需要同时解决两类风险：

1. 上传状态和复制状态使用了同一组终态判断，可能把上传中的 `Transfer=3` 误判为完成。
2. `CopyFile` 默认冲突策略为 `Overwrite`，同名文件或不同站点的同名作品存在覆盖风险。

另外，复制任务卡住时，现有页面只有重新检测和上传确认，缺少暂停、继续、重启和取消能力；远程目录变化主要依赖轮询，诊断信息也不足。

## 目标

- 只有 CloudDrive2 明确报告上传成功完成时，任务才可进入已交付状态。
- 所有 CD2 内部复制遇到重名都自动改名共存，绝不覆盖已有文件。
- 状态机使用 API 返回的实际复制结果路径，不依赖猜测出来的原始文件名。
- 提供单任务复制和上传控制，避免全局误操作。
- 复制结果确认前执行必要的目录缓存刷新和目标验证。
- 使用官方 `PushMessage` 加快远程目录和传输状态更新，断线时回退到轮询。
- 提供 CD2 版本、运行资源和文件句柄诊断，同时兼容不支持新 API 的旧服务。
- 保持严格 `.iso` 上传过滤，不通过 RemoteUpload 绕过现有挂载上传链路。

## 非目标

- 不用 CloudDrive2 API 直接上传本机文件。
- 不删除、覆盖或重命名用户已有的远程文件。
- 不把没有明确 `V1/V2/V3` 的版本纳入自动替换。
- 不改变不同站点同片共存规则。
- 不提供危险的“取消全部上传/复制”快捷操作。

## 实施顺序

实现必须按以下顺序推进：

1. 修复上传状态误判。
2. 处理 `CopyFile` 冲突策略和跨站点共存。
3. 接入官方 `PushMessage`。
4. 增加复制/上传任务控制和 CD2 诊断页。

后续阶段不得以新增功能掩盖前一阶段未通过的安全验收。

## 设计

### 1. 上传状态安全判断

复制任务和上传任务分别维护终态集合。上传成功只认 `UploadFileInfo.Finish`（当前 proto 值为 `5`）及兼容的明确字符串表示；`Transfer`、`Pause`、`Inqueue`、`Preprocessing`、`Cancelled`、`Skipped`、`Error` 和 `FatalError` 都不能直接标记为成功。

当状态字段不可用时，字节进度只能作为观测信息，不能单独触发已交付或源文件清理。若服务端报告完成但目标大小或 ISO 校验不满足，仍保持待确认或失败状态。

### 2. 复制冲突与实际路径

封装远程候选和文件浏览器的 CD2 复制统一调用 `CopyFile` 的 `Rename` 冲突策略，并开启递归冲突处理。调用层需要兼容当前 `clouddrive2-client` 未暴露冲突参数的情况，通过项目内适配方法或 proto stub 设置请求字段。

复制响应中的 `resultFilePaths` 持久化到拉取记录和文件操作记录。状态机优先使用这些实际路径；当响应没有返回路径时，复制任务完成后刷新目标目录，通过 API 返回的路径确认唯一结果，不能把同名目录的猜测路径当成已完成证据。

远程拉取的本地状态键必须能区分不同源路径。若多个源路径最终映射到同一 basename，必须保留独立记录和独立本地路径，不能让后一个任务覆盖前一个任务的状态或文件。

### 3. 官方推送与轮询回退

增加独立的后台推送客户端订阅 `PushMessage`。处理器只负责记录事件和提交轻量复查任务：

- `FILE_SYSTEM_CHANGE`：对受影响的源目录或目标目录做防抖刷新，并触发候选/结果复查。
- `UPLOADER_COUNT`、`DOWNLOADER_COUNT`、`COPY_TASK_COUNT`：使传输状态缓存失效并安排一次队列刷新。
- `FORCE_EXIT`：标记 CD2 认证失效，关闭推送连接，等待下一次认证。
- 流异常：指数退避重连，达到连接上限时恢复现有轮询。

推送连接不能占用 Flask 请求线程，也不能在消息处理器中执行大目录扫描。API Token 需要显式授予最小的 `allow_push_message` 权限；未授权或服务端返回 `UNIMPLEMENTED` 时只关闭推送，不影响轮询和封装流程。

### 4. 任务控制

新增服务端任务操作接口，操作前必须重新读取当前 CD2 任务，并按 API 返回的源路径、目标路径或上传 key 精确匹配。支持：

- 复制：暂停、继续、重启、取消。
- 上传：暂停、继续、取消。

只允许操作当前任务列表中存在且未完成的任务；目标消失、路径不匹配或 API 状态不完整时拒绝操作。每次操作记录结果并立即刷新队列。前端只显示可安全执行的单任务按钮，不提供全局控制。

### 5. 目录缓存和结果验证

复制任务结束或目标首次查找不到时，优先调用 `ForceExpireDirCache` 使相关远程目录缓存递归失效，再调用 `FindFileByPath` 和 `GetSubFiles(force_refresh=True)` 验证目标。API 错误和目标不存在必须区分，不能把连接失败当成文件缺失。

对需要判断原盘完整性的候选，按需调用 `GetFileDetailProperties` 获取总文件数、目录数和总大小；扫描 149 个目录时不对每个目录额外发起详情请求，避免放大 API 压力。

### 6. 诊断与兼容性

增加只读诊断接口，读取：

- `GetRuntimeInfo`：CloudDrive2 服务版本和 Cloud API 版本。
- `GetRunningInfo`：CPU、内存、缓存、临时文件和传输速度。
- `GetOpenFileHandles`：定位 ISO、临时文件或挂载目录被占用的问题。
- `GetAllTasksCount`：作为队列快速摘要和轮询优化依据。

新 RPC 统一处理 `UNIMPLEMENTED`、认证失败、权限不足和连接中断。诊断失败不影响主流程，并在状态中明确显示“诊断不可用”。

## 错误处理与安全边界

- 不因上传队列暂时为空、分页失败或 CD2 断线而标记上传完成。
- 不因复制任务从 `GetCopyTasks` 消失而直接认定复制成功，必须验证远程结果和本地挂载结果。
- 不因 `CopyFile` 返回成功就删除本地源，必须经过现有 ISO 校验和目标结果确认。
- 所有复制路径由服务端根据当前配置和任务列表解析，不能信任前端直接传入的目标路径。
- 非严格 `.iso` 路径继续从上传状态匹配、进度展示和完成判定中排除。

## 测试

- 用 `Transfer=3` 且进度未完成的上传对象验证不会标记完成。
- 用 `Finish=5` 的上传对象验证可进入完成判断。
- 验证错误、取消、跳过状态不会进入已交付。
- 验证 `CopyFile` 请求使用 `Rename`，不同源路径同名时不覆盖且保存实际结果路径。
- 验证复制任务控制只接受当前精确匹配的源/目标，拒绝不存在或已完成任务。
- 验证推送断线、未授权和 `UNIMPLEMENTED` 时回退轮询。
- 验证目录缓存刷新失败不会被解释为目标缺失。
- 保留现有版本替换、严格 ISO、自动拉取认领和 35 个基础测试。

## 验收标准

1. 上传中的 ISO 不会被提前显示为已上传，也不会触发基于错误状态的清理。
2. 不同站点或同名源的 CD2 复制不会覆盖已有文件，两个结果都能在状态中追踪。
3. 卡住的复制/上传任务可以在页面上进行单任务暂停、继续、重启或取消。
4. CD2 目录缓存、推送断线和旧版本 API 不会让主封装流程卡死或误报成功。
5. 所有新增行为有自动化测试覆盖，且不改变严格 `.iso` 上传约束。
